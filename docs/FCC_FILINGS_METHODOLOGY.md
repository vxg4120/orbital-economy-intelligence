# FCC Filings Methodology

**Version 1.0, 2026-08-24.**

This document is the normative definition of every number that the FCC filings feature
publishes: the pending applications list, the extracted specification views, the docket views,
and the docket timeline endpoint. Any change to a harvest rule, a detection anchor, a parsing
rule, a validation rule, or a serving rule bumps the version here and is recorded in the
Changelog at the bottom.

## 1. Purpose

The feature tracks pending FCC space-station applications: filings that have been submitted to
the Commission and have received no grant, denial, dismissal, or surrender. As of 2026-08-24
there are 667 of them. This is the platform's forward-looking layer, because an FCC
filing precedes launch by months to years: Starlink Gen1 was filed 14 months before its
first launch, and Kuiper was filed 39 months before its first launch. A pending application
can describe satellites that exist in no tracking catalog yet, and a pending modification can
describe changes to satellites that are already flying.

The feature goes one step beyond the registry. It opens the filings themselves and extracts the
proposed technical specifications (orbital planes, frequency bands, satellite counts) from the
Schedule S Tech Reports that applicants attach, and it publishes every extracted value with a
citation to the physical page it was found on. Where the data cannot support a number, the
number is absent and the coverage section says why.

## 2. Data sources

| Source | Role | Reference |
|---|---|---|
| FCC IBFS bulk data | Application registry: file numbers, applicants, status dates, callsigns, and docket membership. "Pending" is date-defined: filed, with no grant, denial, dismissal, or surrender date. | https://licensing.fcc.gov, public domain |
| FCC filing attachments | The documents behind each filing: Schedule S Tech Reports, legal narratives, and other exhibits, fetched from the FCC's document gateway | https://licensing.fcc.gov |
| This repository | Harvest, blob cache and hashing, content-anchor detection, deterministic parsing, per-field citation, independent validation, serving | this repository |

Schedule S Tech Reports are generated by the FCC's own filing tool in a fixed label-value
layout, which is the property the whole extraction approach rests on: the layout is a machine
artifact, not applicant prose.

## 3. The pipeline

### 3.1 Harvest

Document inventories are harvested per filing from the FCC's document gateway. The harvest and
the spec extraction both run inside the nightly refresh behind weekly staleness gates, and both
last ran 2026-08-24. As of that run, 136 of the 667 pending filings have harvested document
inventories, and those inventories hold 1,313 document rows in total.

### 3.2 Blob cache and hashing

Fetched documents are records their sha256 content hashes and page counts. The bytes themselves are not retained, so a reissued attachment is detectable on refetch, but re-verification depends on the FCC continuing to serve the document. The cache
currently holds 95 documents, of which 67 were fetched whole and 28 arrived truncated. All 28
truncated documents belong to one 2016 filing (SATLOA2016062200058), and the truncation is
server-side on the FCC gateway: 455 bytes delivered against a declared length of 87,684 bytes,
identical under four different clients. Section 6 leads with this.

### 3.3 Content-anchor detection

Documents are identified by what their text contains, never by what they are named. A Schedule
S Tech Report is recognized by content anchors ("OMB 3060-0678", "312 File Number:", "Select
Orbit Type"), each of which is present in 3 of 3 sampled generated reports. Filenames carry no
reliable signal: the strings "Schedule S" and "Form 312" appear in 0 of 3 generated reports,
and the corpus holds 558 distinct document names. Any filename-based rule would therefore be
guessing; the anchor rule reads the document and checks for the fixed strings that the FCC's
own filing tool emits.

### 3.4 Deterministic parsing

Extraction is deterministic: regular expressions over pypdf-extracted text. No language model
is used anywhere in the pipeline, which means every extraction is reproducible byte-for-byte
from the cached document and there is no sampling, no temperature, and no model version to
pin. This is viable because the Schedule S layout is fixed and machine-generated. Narratives
were measured to contain no numeric orbital parameters; they carry intent and legal argument,
so the numeric extraction targets Schedule S reports and does not attempt to parse prose.

### 3.5 Per-field citations

Every extracted value carries the physical page it was found on, and the citation is recorded
per field rather than per record, because a plane's values straddle page breaks in practice: on
the Boeing V-band filing, 17 of its 74 orbital planes carry inclination on one page and apogee
and perigee on the next. A record-level citation would be wrong for those 17 planes; a
field-level citation is exact for all of them.

### 3.6 Independent validation

Before a row becomes servable, an independent validator re-opens each cited page and confirms
that the value's tokens are actually present on it. Extraction and validation share no code,
so a parsing bug cannot vouch for its own output: the two implementations have to agree on the
same page before a value is served.

### 3.7 Serving rules

Rows that fail validation are stored but never served, and 100 percent of currently served
rows passed page-level validation. Values are served exactly as filed, including values that
are physically implausible: the lunar sentinel rows described in section 6 are served with the
applicant's placeholder numbers, flagged `as_filed_implausible`, and excluded from summary
altitude ranges with the exclusion counted visibly rather than silently. Specs are never
merged across filings: each filing's extracted rows stand alone with their own citations.

## 4. The docket model

Dockets are modeled as timelines keyed on callsign, never as supersession chains, for two
reasons that the data itself imposes.

First, the bulk data has no parent-filing key. There is no field that says which earlier filing
a modification amends, so any chain would be an inference presented as a record.

Second, concurrent pending modifications are the normal case, and a chain has no honest way to
order them. The evidence is callsign S3069 (SpaceX Gen2): the docket holds 28 filings since
2022-12-15, of which 19 are granted and 9 are pending, and 4 of the pending filings serve
validated specs. Four of the pending filings are concurrent MODs, each modifying a different
aspect of the same authorization. A supersession chain would have to pick an order among them
that the record does not contain; a timeline presents them as what they are, simultaneous
open requests against one authorization.

This is not an edge case. Across all SAT filings there are 1,361 dockets, 674 of them hold
more than one filing, and 347 pending filings sit in multi-filing dockets. Because specs are
never merged across filings, a docket view shows each filing's extracted specification
separately, with its own citations, in filing-date order.

## 6. Known limitations and biases

* **28 of the 95 cached documents are truncated, and the platform cannot fix that.** All 28
  belong to one 2016 filing, SATLOA2016062200058, and the truncation is server-side on the FCC
  gateway: 455 bytes delivered against a declared length of 87,684 bytes, reproduced
  identically under four different clients. Those documents cannot be parsed, and no
  specification will be extracted from that filing until the FCC serves the full bytes.
* **Schedule S exists for 64 of the 136 harvested filings, and specs are served for 60.** The
  extraction layer covers a minority of the pending pipeline: 103 of the 136 harvested filings
  carry a narrative or a Schedule S PDF, which means 33 carry neither, and 667 minus 136,
  which is 531, pending filings have no harvested inventory at all yet. Every aggregate over
  extracted specs (satellite totals, plane counts, band counts) describes the covered slice,
  not the whole pending pipeline, and understates the industry accordingly.
* **Narratives carry no numeric orbital parameters.** This was measured, not assumed: the
  narrative attachments contain intent and legal argument, so for a filing without a Schedule S
  Tech Report there is nothing numeric to extract, and the feature serves no specification for
  it rather than inferring one from prose.
* **Lunar missions file placeholder orbits, and they are served as filed.** Schedule S has no
  field for a translunar trajectory, so applicants enter sentinels: Intuitive Machines and
  Lockheed Martin file apogee 1 km, perigee 1 km, and inclination 0, and Astrobotic files
  apogee 99999 km. The 4 affected orbital-plane rows are served exactly as filed, flagged
  `as_filed_implausible`, and excluded from summary altitude ranges with the exclusion counted
  visibly. The feature reports what was filed; it does not correct a form that cannot express
  the mission.
* **No supersession and no field inheritance.** Because the bulk data has no parent-filing key
  and specs are never merged across filings, the feature cannot answer "what is the current
  authorized configuration of this system." A docket timeline shows every filing side by side,
  and on a docket like S3069, with 4 concurrent pending MODs each modifying a different
  aspect, assembling the effective configuration would require legal judgment that the
  pipeline deliberately does not exercise.
* **The extracted layer is machine-derived and is kept out of headline metrics.** Every served
  value comes from deterministic parsing of a PDF, validated against its cited page, but it
  remains a reading of a filing rather than a catalog observation. Totals such as the 5,246
  proposed satellites appear inside the filings feature with their denominators attached, and
  they do not enter the platform's headline fleet or behavior metrics, which count only
  spacecraft that have launched and been catalogued.

## 7. Corrections

Applicants and readers can dispute any extracted value: email vibhavgupta2@gmail.com with the
subject "FCC filings: {file number}". Include the document, the page, and the value in
dispute. Because every document is cached with its sha256 content hash and every value carries
a per-field page citation, a dispute is checkable against the exact bytes that were parsed,
even if the FCC has since reissued the attachment.
